# FMIndex 운영 매뉴얼

## 1. 운영 목적

이 문서는 FMIndex의 수집·분석·집계 파이프라인을 안전하고 재현 가능하게 운영하기 위한 기준이다. 초기 운영은 연구형 로컬 환경을 전제로 하며, 외부 공개 전에는 별도의 정책·보안·부하 검토를 수행한다.

## 2. 운영 원칙

1. 수집기는 기본적으로 꺼진 상태에서 시작한다.
2. 새로운 데이터 원천 또는 파서 버전은 반드시 dry-run과 fixture 테스트를 거친다.
3. 429, 접근정책 변화, CAPTCHA, 인증 요구가 감지되면 우회하지 않고 중단한다.
4. 원문 수집량보다 누락률·중복률·실패율을 먼저 측정한다.
5. 지수는 수집·분석 상태가 정상일 때만 새 스냅샷으로 발행한다.
6. 모델·프롬프트·산식 변경은 버전을 올리고 이전 결과를 보존한다.
7. 장애를 숨기기 위해 마지막 정상 값을 현재 값처럼 표시하지 않는다.

## 3. 일상 실행 절차

```powershell

```

확인 항목:

- 현재 브랜치와 커밋
- `.env` 존재 여부
- Node.js·pnpm 버전
- 데이터·로그 디렉터리
- 로컬 LLM 서버 상태
- 수집기 활성화 여부
- 전회 실행의 비정상 종료 여부

### 3.2 수집기 활성화 전 승인 체크

다음 조건을 모두 충족하기 전에는 `COLLECTOR_ENABLED=true`로 변경하지 않는다.

- 데이터 원천의 접근 범위와 정책을 검토했다.
- 목록 페이지 fixture가 저장돼 있다.
- 파서 단위테스트가 통과한다.
- 요청 간 최소 지연과 동시성 1이 설정돼 있다.
- 429 즉시 중단이 활성화돼 있다.
- 원문 만료 작업이 구성돼 있다.
- 운영자가 중단 방법을 알고 있다.

### 3.3 정상 종료

- 현재 요청을 마친 뒤 신규 작업 투입을 중지한다.
- 체크포인트와 마지막 성공 ID를 저장한다.
- 실행 요약을 기록한다.
- 부분 저장된 응답은 quarantine으로 이동한다.
- 재시작 시 같은 게시물을 중복 처리하지 않는지 확인한다.

## 4. 수집 상태 정의

| 상태 | 의미 | 운영 조치 |
|---|---|---|
| `DISABLED` | 설정상 비활성 | 승인 전 정상 상태 |
| `HEALTHY` | 요청·파싱 정상 | 계속 운영 |
| `DEGRADED` | 일부 실패·지연 | 요청량 감소, 원인 확인 |
| `BACKING_OFF` | 오류 후 대기 | 재시도 횟수와 간격 확인 |
| `STOPPED_BY_429` | 요청 제한 감지 | 당일 자동 재개 금지, 수동 검토 |
| `STOPPED_BY_POLICY` | 정책·접근 구조 변화 | 운영 중단, 정책 재검토 |
| `FAILED` | 복구 불가능 오류 | 체크포인트 보존 후 수동 복구 |

## 5. 기본 안전 한도

초기 기본값:

- 목록 확인 간격: 10분
- 상세 요청 동시성: 1
- 상세 요청 간 지연: 3~7초 랜덤
- 요청 타임아웃: 20초
- 자동 재시도: 최대 2회
- 429 발생: 즉시 수집 중단
- 원문 기본 보존: 7일
- LLM 동시성: 1
- 공개 데이터 지연: 최소 15분

실측 데이터 없이 요청 주기를 더 공격적으로 줄이지 않는다.

## 7. 장애 대응

### 7.1 HTTP 429

즉시 조치:

1. 수집기를 `STOPPED_BY_429`로 전환한다.
2. 자동 재시도를 중단한다.
3. 발생 시각, 직전 1시간 요청 수, URL 유형을 기록한다.
4. 세션·프록시·User-Agent 변경으로 우회하지 않는다.
5. 최소 다음 운영 주기까지 수동 검토 없이는 재개하지 않는다.

재개 조건:

- 요청량 원인을 확인했다.
- 수집 간격을 늘렸다.
- 동일 원인 재발 방지 테스트를 추가했다.
- 운영 기록에 재개 근거를 남겼다.

### 7.2 DOM 또는 파서 변경

징후:

- 목록 결과 0건
- 게시물 ID 추출률 급락
- 제목·시간 필드 공백 증가
- 동일 HTML에서 파싱 결과 변동

조치:

1. 실제 수집을 중단한다.
2. 실패 응답을 제한된 fixture로 보존한다.
3. 어댑터 수정과 회귀테스트를 작성한다.
4. dry-run에서 신규·중복 판정이 정상인지 확인한다.
5. 버전을 올린 후 재개한다.

### 7.3 LLM 분석 오류

- JSON 스키마 실패는 최대 1회 교정 요청 후 quarantine으로 보낸다.
- 동일 입력 반복 실패 시 무한 재시도하지 않는다.
- 모델 서버 지연 시 수집과 분석을 분리해 원문 만료 전에 backlog를 관리한다.
- 모델 교체 시 비교 표본을 만들고 기존 분석을 덮어쓰지 않는다.

### 7.4 지수 이상치

징후:

- 한 게시물이 전체 지수의 과도한 비중 차지
- 유효 표본이 적은데 극단값 발생
- 지수가 짧은 시간에 반복적으로 0·100 근처 이동
- 활동량은 낮은데 관심도지수 급등

조치:

1. 상위 기여 레코드를 확인한다.
2. 중복·도배·참여도 상한을 검증한다.
3. 데이터 신선도와 표본 수를 확인한다.
4. 산식 버그면 해당 시간창을 무효화한다.
5. 수정 후 새 산식 버전으로 재집계한다.

### 7.5 디스크 사용량 증가

- Raw 만료 작업이 동작하는지 확인한다.
- quarantine과 로그의 보존 기한을 확인한다.
- 모델 파일과 데이터 백업을 같은 디렉터리에 두지 않는다.
- 삭제 전에 실행 ID와 보존 대상 목록을 남긴다.
